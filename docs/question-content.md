# Database question content

There is no operational question bank in source code, static assets, seed fixtures or deployed runtime modules. Catalog metadata is initialized separately. `db:seed` can create one development-only administrator; it does not create questions or fake quiz histories. Tests use deliberately synthetic tokens in an isolated test database.

The October 2026 collection is `lunaris-core-2026-10`: 780 original source-based questions, 30 per topic across 26 topics. Each topic has 10 FOUNDATIONAL, 10 INTERMEDIATE and 10 ADVANCED questions. Technical questions include single and multiple selection; interpersonal questions use scenario quality rubrics. The concepts were selected for core interview and practical relevance; no measured interview-frequency ranking is claimed. Sources include MDN, TypeScript/React/Next.js/Node.js/Express/Hono/PostgreSQL/GraphQL/Git documentation, OWASP, Playwright/Vitest, Google SRE/re:Work, CCL, Scrum Guide and TeamSTEPPS. Wording is original, rather than a copied third-party question bank.

Every collection question stores provenance in its immutable JSONB content: collection ID, original authorship, source URLs/titles/access date, learning objective and difficulty rationale. Finalized answer review exposes references for further reading. Active questions omit provenance, explanations and grading keys. Difficulty and interpersonal weights are editorial; independent domain review and statistical calibration remain future quality work.

Default future attempts use Easy 10 questions / 20 minutes (8 foundational + 2 intermediate), Medium 15 / 30 minutes (3 + 9 + 3), Competitive 15 / 25 minutes (0 + 6 + 9). Config changes do not alter existing attempt snapshots. Selection uses exact largest-remainder apportionment and prefers unseen questions within each required level. A difficulty shortage makes a mode unavailable and fails before consuming quota; it never silently substitutes another difficulty. Repetition remains possible when the user's requested set exhausts unseen content.

To import an externally maintained collection, use `pnpm db:content /absolute/private/import.json`. The envelope contains `collectionId`, `expectedPerDifficulty` (at least 10), `legacyQuestionKeys` and a `document` matching the strict OpenAPI import schema. The operator verifies all active topics, level counts, prompt/option uniqueness, source metadata, rubrics and grading bounds before privately staging the questions. Publication, legacy archival, unmodified-default policy upgrades and the collection audit record are committed together. Staging content is immutable; conflicting edits require a new version. No historical attempt, answer, result, reward or rating event is deleted or recalculated. Older custom versions of legacy keys are preserved.

Production import requires an explicit production operator build and `QUESTION_IMPORT_FILE`. Private documents must never be committed, placed in public assets or included in normal deployments. `.vercelignore` uploads only build inputs; an operator temporarily includes a private document for import, removes it, and follows with a content-free release. Ordinary `db:release` initializes metadata only. Database content is the source of truth and must be covered by database backup and restore procedures.

`pnpm db:audit` prints safe counts and mode availability from the actual database without answer keys. `QUESTION_COLLECTION_ID` can restrict the audit to one collection. Publication and policy changes have immutable audit records. Admin imports remain available for externally authored documents of up to 1000 questions per atomic batch.
